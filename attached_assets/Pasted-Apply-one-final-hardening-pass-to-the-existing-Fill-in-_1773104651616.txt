Apply one final hardening pass to the existing “Fill in the gaps” feature. Do not rebuild anything. Make targeted improvements on top of the current working implementation.

Goal:
Close the remaining gaps so the feature is truly production-safe, fully traceable, and easy to QA.

Tasks:

1. Enforce server-side validation to match client-side validation
Right now the modal validates uploads and URLs on the client. Make sure the backend enforces the same rules too.

Requirements:
- Validate supporting file MIME type server-side
- Validate supporting file size server-side
- Reject unsupported files even if they bypass client checks
- Reject oversized files even if they bypass client checks
- Validate supporting links server-side
- Normalize valid URLs server-side
- Return clear error messages for invalid submissions
- Never trust client-side validation alone

2. Restrict supporting links to safe URL schemes only
The current URL constructor validation is not enough.

Requirements:
- Only allow http:// and https:// URLs
- Reject javascript:, data:, file:, ftp:, mailto:, and any other non-http/https schemes
- Normalize URLs after validation
- Preserve the validated URL in storage
- Show a clear inline error if the scheme is not allowed

3. Make SEO HQ timeout / fallback state fully observable
The engine already times out and falls back gracefully. Make that state more visible and traceable.

Requirements:
- Ensure seoHqLoadStatus always clearly records whether the load was:
  - loaded
  - partial
  - timeout
  - unavailable
- Surface that state clearly in the Clarification Trail UI
- Store that state in the session metadata consistently
- Do not silently fall back without leaving an audit trail
- Keep fallback behavior non-blocking for report generation

4. Add “Used in report” visibility to Clarification Trail
Add a simple internal marker beside each answered clarification item showing whether it actually influenced the final generated report.

Purpose:
We need to distinguish between:
- collected but not used
- collected and used

Requirements:
- Add a “Used in report” indicator beside each answer in Clarification Trail
- If possible, support a second state like:
  - Used in report
  - Not used
- If finer detail is available, allow:
  - Used in narrative
  - Used in recommendation
  - Used in priority framing
  - Used in caveat/confidence note
- Keep the UI compact and internal-only
- Do not fake usage; only mark something as used if the report generation pipeline actually consumed it

Implementation guidance:
- Track which clarification answers, links, or files are referenced during final report generation
- Persist lightweight usage metadata with the generated report or linked gap session
- Preserve traceability back to questionId

5. Strengthen session resume / refresh behavior
The feature already has idempotency guards. Now harden session recovery.

Requirements:
- If the user refreshes mid-modal, attempt to resume the in-progress session where feasible
- If the same in-progress session is reopened, do not create a new session
- Preserve already entered answers where feasible
- Preserve uploaded file/link associations correctly
- Ensure final submission still only generates one report
- Ensure retries do not duplicate answers, files, or sessions

6. Add manual QA / smoke-test coverage for all report types
Create a lightweight but clear QA pass for:
- Bi-Weekly
- Monthly
- QBR Prep
- QBR Full
- Mid-Strategy

Test scenarios:
- Fill in the gaps unchecked → normal generation unchanged
- Fill in the gaps checked but no questions returned → report generates immediately
- Fill in the gaps checked with questions returned → modal flow works
- All questions skipped
- One important answer entered
- Supporting link attached
- Supporting file attached
- Invalid file rejected
- Oversized file rejected
- Invalid URL rejected
- Non-http/https URL rejected
- SEO HQ loads successfully
- SEO HQ times out / is unavailable
- Refresh during modal
- Double-click generate
- Double-submit final step
- Clarification Trail renders correctly
- “Used in report” markers appear correctly

Requirements:
- Document the expected result for each test
- Confirm no regressions to the existing generate flow
- Confirm question-to-attachment traceability remains intact

7. Guardrails
- Do not regress the current working feature
- Do not remove the max 6 question cap
- Do not remove graceful fallback behavior
- Do not allow unsafe URL schemes
- Do not rely only on client-side validation
- Do not mark clarification content as “used” unless it actually influenced generation
- Do not create duplicate sessions or duplicate reports
- Do not break existing Clarification Trail behavior

8. Acceptance criteria
This pass is complete when:
- backend validation matches frontend validation
- only http/https supporting links are accepted
- SEO HQ fallback state is clearly stored and visible
- Clarification Trail shows whether each answer was used in the final report
- in-progress sessions recover more safely after refresh/reopen
- duplicate sessions/reports remain prevented
- smoke tests are completed across all 5 report types
- current working UX remains intact

Deliverables:
- code changes implementing the above
- updated Clarification Trail with “Used in report” status
- any necessary schema/storage changes
- QA notes or test summary confirming the smoke tests passed
