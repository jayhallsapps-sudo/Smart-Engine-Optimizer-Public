Run a controlled hardening and cleanup pass on SmartEO based on the latest audit findings.

This is a fix pass, not a feature expansion pass.

IMPORTANT SAFETY RULE:
Do not prove destructive issues by actually deleting or mutating live records.
Do not validate vulnerabilities by destroying data, overwriting records, or modifying production-like content.
For any risky verification, use:
- code inspection
- non-destructive dry-run checks
- test-only temporary records clearly labeled
- read-only validation
- mocked requests where possible

Do not delete, patch, or overwrite real client data unless the task below explicitly requires removal of legacy/dead system artifacts.

==================================================
PRIMARY GOAL
==================================================

Fix the launch-blocking and high-priority issues identified in the audit, while preserving current report functionality.

Prioritize:
1. security hardening
2. data integrity
3. persistence correctness
4. safe fallback behavior
5. route cleanup
6. reliability hardening
7. UX cleanup where directly tied to report workflows

Do not redesign the app.
Do not rebuild working report generators unless required for the fixes below.

RULES OF ENGAGEMENT
==================================================

- Do not perform destructive validation on live data.
- Do not leave dual systems in place if one is officially deprecated.
- Prefer explicit errors over silent fallback.
- Prefer visible “Manual entry needed” / “Data unavailable” states over fabricated numbers.
- Preserve current working report behavior where not directly affected.
- If a fix requires a migration or cleanup, do it safely and explain it.
- If a route is dead/legacy and no current UI uses it, remove it.

==================================================
1. API ROUTE PROTECTION
==================================================

Problem:
There is currently no meaningful protection on API routes.

Implement the best practical protection available for the current SmartEO environment.

Requirements:
- Add a consistent protection layer for all API routes.
- Since this is currently an internal tool, a practical first version is acceptable, but it must be real protection.
- Choose the strongest realistic option for the current app architecture. Examples may include:
  - shared secret header middleware
  - session-based gate
  - IP allowlist if appropriate
  - environment-based internal access guard
- Protect all API routes, including report generation, export, saved reports, crawl assets, setup/config, and utility endpoints.
- Do not break the existing app frontend. If the frontend must send a token/header, wire it cleanly.

Deliverable:
- one consistent route-guard pattern across the app

==================================================
2. OWNERSHIP / SCOPE VALIDATION ON PATCH / DELETE
==================================================

Problem:
ID-only PATCH/DELETE endpoints can modify or delete any record.

Fix:
- For every PATCH / DELETE route acting on client-owned data, validate ownership/scope before acting.
- Look up the record first.
- Confirm it belongs to the expected client/report context.
- Reject the action if context does not match.

Apply this to:
- saved reports
- crawl assets / SF reports
- call tracking uploads
- any report-specific save systems still remaining
- any other mutable client-scoped records

Do this without destructive proof on live data.

==================================================
3. REMOVE SILENT MOCK-DATA SUBSTITUTION IN CLIENT-FACING REPORTS
==================================================

Problem:
Permission failures and integration failures are silently replaced with mock data.

Fix:
- Stop silently substituting fabricated mock data in client-facing reports.
- If a source is unavailable, show a clear unavailable state in the report generation flow and output.
- Use:
  - Manual entry needed
  - Data unavailable
  - Connection issue
  - or similar explicit messaging
- Keep the report structure stable.
- Do not drop slides/sections just because a source is unavailable.

Important:
- Mock data may still be acceptable for developer-only testing paths, but it must not quietly appear in real report outputs.

==================================================
4. POPULATE sourceSnapshotJson
==================================================

Problem:
sourceSnapshotJson exists but is never populated.

Fix:
- Populate sourceSnapshotJson for all report types when reports are generated and saved.
- Save the source-backed context that created the report, at a reasonable level of detail.
- Include:
  - client ID
  - report type
  - selected date range / period
  - selected current crawl asset ID
  - selected comparison crawl asset ID
  - AM inputs
  - normalized source results or a safe summarized snapshot
  - workbook-backed state where applicable
- Do not store unnecessary sensitive payloads if a summarized snapshot is enough.
- Ensure saved reports can be reloaded with meaningful source context.

Apply to:
- Biweekly
- Monthly
- QBR Full
- QBR Prep
- Mid-Strategy

==================================================
5. REMOVE LEGACY QBR PREP SAVE SYSTEM
==================================================

Problem:
QBR Prep still has legacy save paths / records that do not matter.

Instruction:
The old QBR Prep reports do not matter and can be removed from the system.

Fix:
- Remove legacy QBR Prep save routes and table usage if no current UI depends on them.
- Delete legacy/orphaned QBR Prep records if they are no longer needed.
- Make saved_reports the only durable save system for QBR Prep.
- Remove dead code and dead routes tied to the legacy QBR Prep save flow.

Be explicit about:
- what was removed
- what table/routes remain
- why current QBR Prep still works after cleanup

==================================================
6. REMOVE ENCRYPTION FALLBACK
==================================================

Problem:
Encryption currently falls back to a hardcoded key if env secret is missing.

Fix:
- Remove the fallback entirely.
- If required secret(s) are missing, fail fast with a clear startup error.
- Do the same for any static salt behavior that should not be defaulted insecurely.
- Keep current encrypted data usable if possible, but do not allow future insecure startup.

==================================================
7. ADDRESS xlsx VULNERABILITY RISK
==================================================

Problem:
xlsx package has known vulnerabilities.

Fix this the best way possible with the least breakage.

Preferred direction:
- remove or isolate risky XLSX usage if it is not actually needed for current workflows
- prefer CSV-only handling where that is enough
- if XLSX must remain, sandbox or constrain usage as much as possible
- reduce attack surface
- update/replace package if safe and compatible

Requirements:
- explain exactly what usage of xlsx remains after this pass
- if it is removed, explain what replaced it
- if it remains, explain the mitigation

==================================================
8. BODY LIMITS AND RATE LIMITING
==================================================

Problem:
Global 50 MB body limit and no rate limiting.

Fix:
- Replace the one-size-fits-all global body behavior with route-appropriate limits.
- Apply smaller limits to normal JSON routes.
- Use larger limits only where truly necessary, such as export or file upload routes.
- Add rate limiting or equivalent abuse protection to expensive endpoints, including:
  - report generation
  - export
  - upload
  - print-cache if it remains
- Keep internal usability intact.

==================================================
9. SAFE DELETE / SOFT DELETE
==================================================

Problem:
Hard deletes are permanent and risky.

Fix:
- Implement safer delete behavior where appropriate.
- At minimum, avoid irreversible destructive deletion for user-generated/client-scoped content unless there is a strong reason not to.
- If soft delete is feasible, use it for:
  - saved reports
  - crawl assets / uploads
  - other client-owned artifacts
- If a full soft-delete pattern is too heavy right now, implement the safest practical delete protection you can and explain the compromise.

==================================================
10. FIX PRINT TIMING RELIABILITY
==================================================

Problem:
Print/export routes rely on fixed setTimeout before print.

Fix:
- Replace fixed timeout-based print triggering with readiness-based logic.
- Wait for:
  - fonts
  - images
  - major content render
before print/export proceeds.
- Keep existing print/export appearance intact.

==================================================
11. FIX MONTHLY SILENT SLIDE DROPS
==================================================

Problem:
Monthly can still silently omit conditional slides.

Fix:
- Ensure all expected Monthly slides always render in fixed order.
- If data is missing, render placeholder slide content with Manual entry needed or equivalent.
- Do not silently skip sections.

This must align with the existing Monthly v2 spec.

==================================================
12. FIX MID-STRATEGY EMPTY 200 RESPONSE
==================================================

Problem:
Mid-Strategy can return an empty 200 response on certain malformed input paths.

Fix:
- Ensure Mid-Strategy generate either:
  - returns a valid report with expected slide count
  - or returns a proper error response
- Never return an empty success response for an invalid generation request.

==================================================
13. REMOVE DEAD / DUPLICATE ROUTES
==================================================

Problem:
The app has accumulated dead and duplicate routes.

Fix:
- Identify routes that are no longer used by the current UI or current architecture.
- Remove them cleanly.
- Prioritize removing:
  - old QBR Prep legacy routes
  - obsolete export routes if replaced by specific report routes
  - dead history/report paths if superseded

Important:
Do not remove a route unless you verify current UI does not depend on it.

==================================================
14. FIX semrushProjectId BEHAVIOR
==================================================

Problem:
semrushProjectId is stored but non-functional.

Fix one of these two ways:
- either make semrushProjectId actually matter in a real, defensible way
- or remove/deprecate it cleanly so the UI and schema do not imply behavior that does not exist

Do not leave misleading config fields in place.

==================================================
15. FIX AUTOSAVE SILENT-FAILURE PATH
==================================================

Problem:
Autosave can silently fail when pending payload is null at debounce fire.

Fix:
- make autosave behavior explicit and safe
- if there is nothing to save, do not leave UI stuck in unsaved state
- if autosave cannot proceed, surface a meaningful status or retry path
- do not silently drop edits

Apply across the shared useReportSave flow.

==================================================
16. REPORT HISTORY / SAVED REPORT ACCESS
==================================================

Instruction:
A separate History page is not needed for saved reports.
Saved reports should be accessible within each report itself.

Fix:
- ensure each report type has robust in-report saved report selection
- ensure users can load prior reports from within that report page
- where useful, allow prior report selection for comparison within the report workflow
- if the old History page is obsolete or misleading, remove it or narrow it to what it actually does

Do not build a big new history system unless necessary.
Keep it report-native.
