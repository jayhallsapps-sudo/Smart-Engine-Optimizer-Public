Build a major redesign of the report design system inside SmartEO.

The current Theme and Templates modules are too clunky, too fragmented, and too hard to preview. Combine them into one clear design system with two sections only:

1. Theme
2. Templates

The system must be built around one core rule:

Everything designed in-app must be capable of exporting to Google Drive with a near-identical appearance. No design controls should exist if they cannot be rendered reliably in Google Docs or Google Slides. Do not optimize for PDF output. Optimize for Google Drive fidelity first.

OVERALL OBJECTIVE

Create a unified report design system where:

* Theme controls the global visual language
* Templates control the layout and structure of each report type
* Users can preview changes live as they make them
* Templates are WYSIWYG edited with drag-and-drop blocks
* Theme styles automatically apply to templates
* A saved template remains fixed unless the user intentionally edits it
* Exports to Google Docs and Google Slides preserve the in-app design as closely as possible

SECTION 1: THEME MODULE

The Theme module is the global style system. It must control all recurring design elements across every report type.

Build Theme so the user can define and preview:

A. Brand / Global Identity

* Logo upload
* Header style
* Footer style
* Brand colors
* Accent colors
* Background colors
* Font family selection
* Typography scale
* Body text styling
* Heading styles (H1, H2, H3, H4)
* Link styling
* Divider / line styling

B. Table Design System

* Table header background
* Table header font color
* Table body background
* Alternate row background
* Border color
* Border thickness
* Rounded vs square corners
* Cell padding
* Font size
* Boldness / font weight
* Alignment defaults
* Spacing around tables
* Optional row striping
* Optional shadow only if export-safe in Google Drive

C. Chart Design System

* Title styling
* Axis label styling
* Gridline styling
* Legend styling
* Data label styling
* Background treatment
* Border / frame styling
* Color palette limited to export-safe colors
* Only include chart customization options that can be faithfully rendered in Google Slides or Google Docs

D. Content Element Defaults

* Callout boxes
* Insight boxes
* KPI cards
* Bullets
* Numbered lists
* Quote blocks
* Section labels
* Image frame treatment
* Icon treatment if supported safely in export

E. Page / Slide-Level Defaults

* Margins
* Content width
* Section spacing
* Default page padding
* Slide title position defaults
* Page header / footer spacing
* Standard grid behavior

F. Live Preview
Every setting in Theme must update a live preview panel immediately.
The preview must include:

* Header example
* Body text example
* Table example
* Chart example
* KPI / insight box example
* Typical report section example

Users must never have to save blindly to see what they changed.

SECTION 2: TEMPLATES MODULE

The Templates module is the structural editor for each report type.

Build a true WYSIWYG drag-and-drop editor that works similarly to Elementor in WordPress:

* Left sidebar = available elements
* Center canvas = editable page or slide
* Right sidebar = element settings / spacing / positioning / content bindings
* Live preview on the actual canvas
* Drag, drop, resize, move, duplicate, and delete elements visually

IMPORTANT:
Theme controls the styling.
Templates control the layout.
Users should not restyle tables, typography, headers, etc. inside each template unless there is an intentional override system with strict limitations.

SUPPORTED TEMPLATE TYPES

At minimum, support:

* Google Docs-style templates for document outputs
* Google Slides-style templates for deck outputs

Examples of report families this must support:

* Doc-style reports
* Slide-style reports
* Internal and client-facing reports that need different layouts but the same theme system

TEMPLATE BUILDER REQUIREMENTS

A. Template Library
Create a template library where users can:

* View all report templates
* Group templates by report type
* Duplicate templates
* Rename templates
* Archive templates
* Set a default template for each report type
* Preview templates before editing

B. Canvas Behavior
The canvas must visually represent the real output format:

* Document templates should look like document pages
* Slide templates should look like slides
* Page or slide boundaries must be obvious
* Users must be able to move between pages/slides easily
* Multi-page and multi-slide templates must be supported

C. Drag-and-Drop Elements
Support a clean set of reusable blocks/elements:

* Heading
* Text
* Rich text
* Table
* KPI card
* Chart container
* Image
* Logo
* Divider
* Spacer
* Button / CTA block if relevant
* Callout box
* Insight box
* Two-column section
* Three-column section
* Section wrapper
* Header block
* Footer block
* Page number
* Dynamic metric block
* Dynamic text token block
* Repeating data section if applicable

D. Element Controls
For each placed element, allow:

* Position
* Width
* Height where relevant
* Padding
* Margin
* Alignment
* Layer order
* Duplicate
* Delete
* Lock
* Hide
* Bind to data source / token where relevant

E. Grid / Layout Assistance

* Snap to grid
* Guides
* Column structure
* Consistent spacing controls
* Optional rulers
* Safe zones for export

F. Reusable Blocks
Allow saving a layout section as a reusable block.
Example:

* KPI row
* Standard intro section
* Standard performance summary section
* Standard closing section

G. Template Persistence
Once a template is saved, it must not change automatically because the system changed something elsewhere.
Only user-directed edits should change a saved template.
If theme styles update, the system should clearly distinguish between:

* Global style changes that cascade
* Layout changes that do not cascade
  Do not silently mutate saved templates.

GOOGLE DRIVE EXPORT REQUIREMENTS

This is the most important technical requirement.

Build the export layer around Google Drive compatibility, not browser-only rendering.

Exports must support:

* Google Docs for document-style reports
* Google Slides for slide-style reports

The exported file should preserve as much as possible of:

* Typography
* Table styling
* Header/footer appearance
* Layout spacing
* Chart styling
* Section spacing
* Page/slide structure

You must design the in-app system using only controls that can be translated reliably into Google Docs / Google Slides output.

Do not create “pretty but fake” editor controls that cannot survive export.

If something cannot export reliably, one of these must happen:

1. Do not offer the control
2. Or explicitly label it unsupported and disable it for production templates

ARCHITECTURE REQUIREMENTS

Refactor the current system so it is clean and understandable.

Recommended structure:

* Theme Manager
* Template Manager
* Template Canvas Editor
* Reusable Block Library
* Export Renderer
* Google Docs Renderer
* Google Slides Renderer
* Design Token System
* Preview Engine

Use one shared design token layer so Theme settings drive all visuals consistently.

The system must clearly separate:

* Global style tokens
* Template layout definitions
* Export rendering rules

PREVIEW REQUIREMENTS

Preview must exist everywhere it matters:

* In Theme while editing styles
* In Templates while editing layout
* Before export
* During template selection

No part of this redesign should require the user to imagine the result.

UI/UX REQUIREMENTS

Make the experience simple and obvious.

The current system feels confusing and fragmented.
The replacement should feel:

* Clear
* Modern
* Visual
* Fast
* Structured
* Hard to misuse

The UX should reduce decision fatigue.
Do not bury critical controls.
Do not make users bounce between modules to understand what they are editing.

A good mental model is:

* Theme = how everything looks
* Templates = where everything goes

ACCEPTANCE CRITERIA

Do not mark this feature complete unless all of the following are true:

1. Theme and Templates are restructured into one unified design system with those two sections
2. Theme controls global styling for recurring report elements
3. Templates are edited in a true drag-and-drop WYSIWYG canvas
4. Live preview exists for both Theme and Templates
5. Document-style and slide-style templates are both supported
6. Tables, headers, typography, and chart styles are centralized in Theme
7. Template layouts can be duplicated, saved, edited, and reused
8. Saved templates do not change unless the user edits them
9. Export to Google Docs and Google Slides preserves the in-app structure and appearance as closely as possible
10. No design settings are exposed that cannot be rendered reliably in Google Drive exports
11. The system is visually and functionally simpler than the current implementation
12. Reusable blocks are supported
13. Template previews are visible before opening/editing
14. The output in-app and in Google Drive is materially aligned
