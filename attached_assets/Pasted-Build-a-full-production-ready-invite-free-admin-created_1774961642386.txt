Build a full production-ready invite-free, admin-created authentication and authorization system for SmartEO. Do not build a public signup flow. Do not build a partial prototype. Do not stop at UI. Implement the real backend, database, permissions, route protection, session/auth flow, and admin management system now.

High-level objective

SmartEO needs a real multi-user system where:

* users are created only by an admin
* users log in with their own credentials
* access is controlled by module and sub-module permissions
* non-admin users only see and access what they are explicitly allowed to access
* client/account data is separated by user access boundaries
* admins can manage users from an internal admin panel
* no outbound email service is used
* when a user is created or reset, the system generates a temporary password and a copyable credential block for the admin to manually send

Non-negotiable rules

1. No public signup

* No self-serve registration
* No “Create account” flow
* No public onboarding flow
* Users can only be created by an admin inside SmartEO

2. Real login system
   Build a real auth system with:

* login
* logout
* secure password hashing
* secure session handling or equivalent secure auth implementation
* forced password change on first login
* admin-triggered password reset flow
* no email-based reset requirement

3. No transactional email
   Do not integrate email sending.
   Do not require SendGrid, Resend, Postmark, Mailgun, SES, or any other paid email provider.
   Do not send invite emails.
   Do not send password reset emails.

Instead:

* when an admin creates a user, generate a temporary password immediately
* show a one-click copyable credentials block in the UI
* admin manually shares the credentials with the user
* if credentials need to be re-sent later, admin must reset the password, which generates a new temporary password and new copy block

4. Initial creator admin
   Seed the initial creator admin account as:

Email: [jayhallsapps@gmail.com](mailto:jayhallsapps@gmail.com)
Password: SmartEO2740@

This user must be created as a full admin.
Implement the seed safely. Do not scatter these credentials recklessly across the app.
Use environment-aware seed logic or equivalent safe development/initial deployment handling if possible.

5. Admins can create other admins
   Admin users must be able to create:

* standard users
* other admins

Do not restrict admin creation to only the original seeded account unless explicitly designed as a future optional feature.

Core user model

Build the system around:

* Role
* Permissions
* Account State

Role:

* Admin
* User

Account State:

* Active
* Suspended
* First Login Required
* Password Reset Required

Do not collapse all of that into a single vague “status” field.
Split role and account state clearly in both backend and UI.

Permission model

Permissions must be granular. Do not use role-only access.
Roles matter, but module and sub-module permissions must be explicitly assignable.

Modules to support right now:

* AMA
* Prepare a Report
* Past Reports
* Client Info
* Client Integrations
* Integrations
* Discoverability Tool
* Templates
* Theme

Special rule for Prepare a Report:

* access must be split further by report type
* architecture must support multiple report types
* right now only Bi-Weekly is active, but the system must support more later without rework

Example current access profile for a basic admin:

* Prepare a Report

  * Bi-Weekly only
* Past Reports
* Client Info
* Client Integrations
* Integrations

No access to:

* AMA
* Discoverability Tool

Important:
Do not hardcode this sample. Build a flexible permission system so admins can assign any valid combination of module and sub-permission access.

Data access and protection

This system is not just about navigation. It must protect data access properly.

Requirements:

* every protected route must require authentication
* every protected module must require permission
* every relevant backend query must enforce access scope
* frontend hiding alone is not acceptable
* users must not be able to retrieve restricted data by typing URLs manually
* users must not be able to retrieve restricted data by directly calling APIs

Client-related data boundaries must be enforced server-side.
If a full client assignment system does not already exist, build a clean foundation so SmartEO can support per-user client/data separation properly as the platform grows.

Auth flow requirements

Required flows:

1. Login
2. Logout
3. Forced password change on first login
4. Admin-created account with generated temporary password
5. Admin-triggered password reset that generates a new temporary password and invalidates the old password
6. Suspended users cannot log in
7. If a user is suspended while logged in, invalidate their active session/access as soon as practical

Do not build email invite links.
Do not build email reset links.
If there is currently a forgot-password screen, either remove it or replace it with a simple message such as:
“Please contact your administrator to reset your password.”

User creation flow

When an admin creates a new user, the system must:

* collect full name
* collect email
* let the admin choose role:

  * Admin
  * User
* let the admin assign module permissions
* let the admin assign sub-permissions where applicable

  * especially under Prepare a Report → report types
* create the user account
* generate a secure temporary password automatically
* hash and store the password securely
* mark the account as First Login Required or Password Reset Required
* show a visible copyable access block immediately after creation

The temporary password must be shown once at creation time in the UI and included in the copy block.
It must never be recoverable later from the database in plaintext.

Credential copy block

Immediately after a user is created, show a clearly visible text block with a one-click copy control.

Required contents:

SmartEO Account Created

Name: [Full Name]
Email: [Email]
Access Level: [Admin or User]
Temporary Password: [generated temporary password]
Login URL: [app login URL]

Instructions:

* Log in using the email and temporary password above
* You will be required to change your password on first login

Build an actual copy-to-clipboard control.
Do not make this a passive text area only.

Admin panel requirements

Create a real Admin area accessible only to admin users.

Admin access behavior:

* that Admin label must be clickable
* clicking it opens the Admin area

Admin area minimum sections:

Required admin actions per user

For each user, the admin must be able to:

* edit module permissions
* edit sub-permissions
* change role between Admin and User
* suspend user
* reactivate user
* reset password
* generate a new temporary password
* generate and copy a fresh access block after password reset

Password reset behavior

Because plaintext passwords must not be stored, “copy credentials again later” cannot reveal the original password.

Correct behavior:

* admin clicks reset password
* system generates a new temporary password
* previous password is invalidated
* new hashed password is stored
* account is marked Password Reset Required or equivalent
* user must change password at next login
* UI shows a fresh copyable credential block with the new temporary password

Do not fake this by storing readable passwords in the database.
Do not build any “view current password” feature.

Suspend / lock out behavior

Admins must be able to suspend a user with one click from the users table or user detail view.

Required behavior:

* one-click suspend / lock out
* suspended users cannot log in
* suspended users lose access immediately or as soon as practical if already logged in
* suspended state must be visible in the user record
* admin can reactivate suspended users
* reactivation restores access without deleting the account

Do not delete users to accomplish suspension.
Use a real suspended/disabled state.

Sidebar and UI behavior

Enforce the following:

* show only modules the user has permission to access
* hide modules the user does not have access to
* hide report types inside Prepare a Report if the user lacks those sub-permissions
* admin users see Admin in the profile area and/or nav
* non-admin users do not
* unauthorized users who somehow hit a restricted route should see a clear unauthorized state, not a broken page
