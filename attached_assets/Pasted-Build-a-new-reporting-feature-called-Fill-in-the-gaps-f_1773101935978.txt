Build a new reporting feature called “Fill in the gaps” for all report-generation flows.

Core product goal:
Before generating any report, give the AM an optional way to let the system identify missing context and ask smart clarification questions. The purpose is to improve report quality when data, context, interpretation, or account inputs are incomplete, weak, contradictory, or unclear.

This feature must apply to all reports, not just one report type. QBR Prep was only an example. The same feature should work across:
- Bi-weekly report
- Monthly report
- QBR Prep
- QBR Full
- Mid-strategy report
- Any future report type added later

Very important:
This feature should not only look for missing data.
It must also look for missing strategic context based on Webserv SEO HQ foundational rules, directives, practices, SOPs, and operating standards.

That means the question engine should evaluate report readiness through two lenses:
1. Completeness lens:
   Do we have everything we need to generate the strongest possible report?
2. SEO HQ standards lens:
   Does the draft report have enough context to align with how Webserv expects SEO to be practiced, explained, prioritized, and defended?

The goal is not just to fill empty fields.
The goal is to fill the gaps that would make the report weaker, less defensible, less strategic, less aligned with business outcomes, or less consistent with SEO HQ expectations.

WHY THIS FEATURE MATTERS

The AM must remain the strategic owner of the account, not just the operator of an AI tool.
This feature should encourage AM thinking, help surface missing context, and improve report quality when current inputs are not enough to confidently generate a strong report.

The system should act like a smart preflight layer that checks:
- do we have the needed information
- do we understand what matters
- are we missing business context
- are we missing relationship context
- are we missing strategic interpretation
- are we about to generate something that is technically filled out but not actually strong by SEO HQ standards

FEATURE REQUIREMENTS

1. UI placement
- In every report screen, place a checkbox directly above the primary generate button.
- Label: “Fill in the gaps”
- Default state: unchecked
- Helper text below checkbox:
  “Ask follow-up questions before generating if the system detects missing context.”

2. Default behavior
- If “Fill in the gaps” is NOT checked:
  - Preserve current behavior exactly
  - User clicks Generate
  - Report generates immediately with no extra modal or interruption

3. Gap-fill behavior
- If “Fill in the gaps” IS checked:
  - When the user clicks Generate, do NOT generate the report immediately
  - First run a pre-generation analysis pass over all available account and report inputs
  - Review all available sources relevant to the report, such as:
    - connected data sources
    - Screaming Frog data
    - report-specific data
    - AM thoughts / manual inputs
    - priority checks
    - client notes
    - any account-level context already available in the app
    - SEO HQ / Notion board content
    - connected SEO HQ boards and linked operational references
    - relevant SOPs, directives, frameworks, and practices tied to the report type

4. SEO HQ / Notion knowledge base requirement
The system must treat SEO HQ and connected boards as a strategic context layer, not just background reading.

When running the gap analysis, the system should consult relevant SEO HQ guidance to determine:
- what a strong report is supposed to include
- what kinds of interpretation are expected from an AM
- what context should be surfaced before client-facing output
- what risks, blockers, sentiment, dependencies, priorities, or expectation-setting elements may be missing
- whether the report would be weak, incomplete, or not defensible by Webserv standards if generated as-is

Examples of SEO HQ-informed checks:
- Is the report tied to business outcomes, not just traffic?
- Is the likely primary goal framed correctly?
- Are we explaining what changed, why it matters, and what happens next?
- Are we connecting SEO activity to lead quality, conversions, pipeline, VOBs, admits, or business impact where appropriate?
- Are we missing client sentiment or relationship pulse context?
- Are we missing risk, blocker, dependency, or approval context?
- Are we missing a trusted-advisor explanation for volatility, performance shifts, or tradeoffs?
- Are priorities aligned with impact, intent, and business goals?
- Is the report likely explainable and defensible to leadership and the client?
- Are we missing AM interpretation that the system should not invent on its own?

5. Gap analysis logic
The system should only ask questions if:
- the answer would materially improve the output
- the answer is not already available in the connected data or manual inputs
- the question is specific enough to answer quickly
- the question is relevant to the report currently being generated
- the question helps satisfy either:
  - missing information needed for report quality
  - missing interpretation needed for SEO HQ alignment

The system should NOT ask:
- generic filler questions
- duplicate questions
- low-value questions
- questions that can already be inferred with high confidence
- questions that do not meaningfully affect report quality
- questions that violate the spirit of Webserv’s operating standards by asking for performative filler instead of useful judgment

6. Question count rules
- There is NO hard maximum question count
- If there is 1 useful question, show the modal and ask it
- If there are several useful questions, ask all useful questions needed to properly fill the gaps
- If there are no useful questions, do NOT show the modal
- If “Fill in the gaps” is checked and the system finds no meaningful questions, the report should generate immediately like normal
- Do not ask unnecessary questions just because the feature is enabled
- Ask only the questions needed to properly fill in weak or missing context

7. Modal experience
If questions are needed, open a modal with the following UX:

Header:
- Title: “Fill in the gaps”
- Subtitle: “A few quick questions could improve this report.”

Progress UI:
- thin progress bar across the top of the modal
- step indicator such as “1 of 3”, “2 of 7”, etc.

Question body:
- show one question at a time
- support these answer types:
  - short text
  - long text
  - single select
  - multi-select / checkbox
  - yes/no

Question actions:
- Back
- Next
- Skip question
- On final question, replace Next with:
  - “Generate report”

Important modal requirements:
- Skip question must exist on every step
- Questions are optional by design
- The modal should feel lightweight, not like a long-form intake form
- The last submission should immediately trigger report generation
- Preserve answers if user moves back
- If modal closes accidentally, user should be able to resume within the session without losing progress

8. Supporting document / link input inside modal
In addition to answering the question itself, each question step should optionally allow the AM to provide supporting context through either:
- an uploaded supporting document
- a supporting link / URL

Requirements:
- This is optional on every question
- It should not be required to proceed
- The uploaded file or link must be attached to that specific question response
- The system should preserve the relationship between the question and its supporting material
- The report generation system must also be allowed to consider that supporting file or link as part of the broader clarification context during generation
- Supported upload flow should be simple and lightweight
- If a file or link is added, show a small confirmation state on that step

Important:
- Supporting documents and links must be tied to the specific question where they were added
- They should not float as unattached general uploads
- The system may use them more broadly in final generation, but their source question must remain traceable

9. Question generation rules
Each generated question should have:
- id
- prompt
- type
- options array when needed
- placeholder when relevant
- priority score
- machine reason / rationale for why the question was asked
- a field indicating whether that rationale is safe to show to the user
- source category indicating why the question exists, such as:
  - missing_data
  - source_conflict
  - business_context_gap
  - sentiment_gap
  - SEO_HQ_alignment_gap
  - report_narrative_gap
  - priority_gap
  - tracking_confidence_gap
  - blocker_dependency_gap

User-facing questions should be:
- concise
- strategically useful
- easy to answer quickly
- written in plain language

10. SEO HQ-informed prioritization rules
Internal prioritization should favor questions that improve report quality in ways Webserv actually cares about.

Examples:
- client sentiment gaps
- lead quality / conversion interpretation gaps
- recent business change gaps
- tracking-confidence gaps
- missing AM interpretation
- conflicting priority signals
- report narrative ambiguity
- contradictions between sources
- unclear strategic focus
- blockers, approvals, or dependencies that affect delivery or expectations
- missing explanation for volatility or performance shifts
- missing context needed to defend recommendations
- missing context needed to tie SEO work to business outcomes
- missing context needed to support the trusted-advisor style of reporting

11. SEO HQ / report-type alignment
The system should not ask the same kinds of questions for every report.
Question selection should reflect both:
- the report type
- the relevant SEO HQ / SOP standards for that report

Examples:
- Bi-weekly:
  focus more on quick wins, momentum, deliverables, relationship pulse, blockers, next steps, and client alignment
- Monthly:
  focus more on performance trends, what moved the needle, strategic direction, risks, and what’s next
- QBR Prep / QBR Full:
  focus more on quarter narrative, business impact, priorities, strategic shifts, conversion path issues, sentiment, expectation resets, and next-quarter direction
- Mid-strategy:
  focus more on strategic adjustments, why priorities are changing, what evidence supports the change, and whether the shift is defensible

12. Example question types
These are examples only. The system should generate its own questions dynamically based on account context and SEO HQ standards.

Possible examples:
- “Has client sentiment changed at all this quarter?”
- “Were there any recent business, staffing, location, or operational changes not reflected in the data?”
- “Is there anything affecting lead quality that the data alone would miss?”
- “Which issue feels most urgent right now?”
- “Do you agree with the current priority order, or would you change it?”
- “Has tracking been incomplete or unreliable lately?”
- “Is there anything the client is especially focused on for the next quarter?”
- “Does this recommendation need context before it is presented to the client?”
- “Is there a reason this data point appears weak, missing, or misleading?”
- “Are there any client-side blockers, delays, or approvals affecting progress?”
- “Is there any context we should include so performance changes are explained correctly?”
- “Would you describe the relationship pulse as positive, neutral, or tense right now?”
- “Is there anything here that would be technically true but strategically misleading without explanation?”

13. “Why are we asking this?” helper
Add a small optional helper toggle or link under the question:
- Label: “Why are we asking this?”
- When clicked, reveal a short explanation of why the question matters
- Only show this if the rationale is safe and useful to expose
- Keep it brief and plain-language
- Do not overwhelm the user with internal system logic

14. Suggested backend flow
Implement a reusable preflight pipeline like this:

generateReport(reportType, inputs, fillInTheGapsEnabled)

If fillInTheGapsEnabled is false:
- proceed directly to report generation

If fillInTheGapsEnabled is true:
- run analyzeReportGaps(reportType, inputs, accountContext, seoHqContext)
- if no meaningful questions are returned:
  - proceed directly to report generation
- if questions are returned:
  - open clarification modal
  - collect answers, skipped states, and optional supporting files/links
  - keep each supporting file/link attached to the specific question where it was submitted
  - merge clarification responses into report input context
  - generate report using original inputs plus clarification responses and supporting materials

15. SEO HQ context loading
Build a reusable way to load and use SEO HQ / Notion context during gap analysis.

Possible structure:
loadSEOHQContext(reportType, accountType, workflowType)

This should pull or reference:
- foundational rules and principles
- relevant SOPs
- report-specific expectations
- strategic directives
- recurring narrative expectations
- quality standards
- “what strong looks like” guidance

If SEO HQ content cannot be loaded for some reason:
- fail gracefully
- still run the normal gap analysis on account/report inputs
- do not break report generation

16. Data model suggestion
Create reusable structures similar to:

GapQuestion {
  id: string
  prompt: string
  type: "short_text" | "long_text" | "single_select" | "multi_select" | "boolean"
  options?: string[]
  placeholder?: string
  priorityScore: number
  rationale: string
  showRationaleToUser: boolean
  sourceCategory: "missing_data" | "source_conflict" | "business_context_gap" | "sentiment_gap" | "SEO_HQ_alignment_gap" | "report_narrative_gap" | "priority_gap" | "tracking_confidence_gap" | "blocker_dependency_gap"
  sourceReference?: string | null
}

GapAnswer {
  questionId: string
  answerType: string
  value: string | string[] | boolean | null
  skipped: boolean
  supportingLink?: string | null
  supportingDocumentId?: string | null
}

GapAnalysisResult {
  shouldAskQuestions: boolean
  questions: GapQuestion[]
  confidenceScore: number
  notes?: string[]
  seoHqChecksApplied?: string[]
}

17. Persistence and auditability
Store clarification responses with the generated report metadata so they can be referenced later.

Include:
- whether “Fill in the gaps” was enabled
- what questions were asked
- which questions were answered
- which questions were skipped
- any supporting document uploads
- any supporting links
- the question each file or link was attached to
- when answers were submitted
- what SEO HQ rules / standards influenced question selection, if available

This matters because report assumptions and additional context should be documentable and reviewable later.

18. Report usage of answers
Clarification answers must be considered in the report.

That means:
- The report generator must actively consume these answers as part of generation context
- The report should use them in:
  - narrative framing
  - priority interpretation
  - client sentiment interpretation
  - strategic recommendations
  - caveats / confidence notes
  - issue prioritization
  - explaining anomalies
  - resolving ambiguity between data sources
  - improving account-specific context
  - expectation-setting language
  - risk / blocker explanation
  - next-step clarity

Important guardrails:
- Never invent answers for skipped questions
- Never pretend the AM answered something they skipped
- Skipped questions should simply reduce certainty where relevant
- Supporting documents and links should be considered when provided
- If an answer materially changes the meaning of a section, the report should reflect that change
- Supporting files and links may inform the report broadly, but their source question must remain traceable in the data model and metadata

19. Guardrails
- Never invent answers for skipped questions
- Never block report generation if everything is skipped
- Never ask questions whose answers already exist in the system
- Never ask vague filler questions
- Never create a modal if there are no meaningful questions
- Never make the report feel harder to generate than it is today
- Never ignore clarification answers once collected
- Never ignore supporting files or links that the AM provided
- Never ask questions that do not improve the final report
- Never generate questions that conflict with SEO HQ standards when those standards are available
- Never treat rankings or traffic alone as sufficient context when business-impact context is missing
- Never allow a technically complete report to bypass clarification if it is still strategically weak by SEO HQ standards

20. UX details
- Modal should be clean and minimal
- Thin progress bar at top
- Step count visible
- Keyboard-friendly where possible
- Preserve answers when moving backward
- Resume progress within session if modal is closed accidentally
- Clear loading state between final submit and report generation
- Optional file upload and optional supporting link should be visible but unobtrusive
- Skip should remain easy to access on every question

21. Reusability requirement
Architect this as a reusable report-clarification framework, not a single-report feature.
It must work across all current report types and be easy to extend to future report types with report-specific question logic where needed.

22. Acceptance criteria
The feature is complete when:
- checkbox appears above Generate button in all report types
- checkbox is unchecked by default
- unchecked state preserves current report generation flow exactly
- checked state runs a gap analysis first
- gap analysis considers both:
  - report/account completeness
  - SEO HQ / Notion standards and directives
- if no meaningful gaps exist, report generates immediately
- if meaningful gaps exist, modal opens
- modal supports one-question-at-a-time flow
- progress bar and step count are visible
- Skip question exists on every step
- optional supporting document upload exists on each question
- optional supporting link field exists on each question
- each uploaded file or link is attached to the specific question where it was added
- final step generates report
- answers, skips, links, and uploads are stored with report metadata
- question-to-supporting-material relationship is stored and traceable
- report generator consumes clarification inputs and reflects them in the final report
- SEO HQ-informed question logic is reusable for all current and future report types

  - missing data logic

- telemetry for:

  - upload/link attachment rate

  - effect on report quality or edit rate later
