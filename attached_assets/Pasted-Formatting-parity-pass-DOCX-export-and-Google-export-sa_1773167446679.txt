Formatting parity pass — DOCX export and Google export/save must visually follow the PDF/preview design as closely as the target format allows.

Current problem:
The PDF/preview design looks polished and is the visual standard. DOCX and export-to-Google currently do not preserve that design language closely enough. Page breaks are acceptable, but the formatting is breaking down too much.

Goal:
Make DOCX and Google export feel like the same report design as the PDF/preview, not a raw fallback version.

Core principle:
PDF/preview is the design source of truth.
DOCX and Google export should match that hierarchy and styling as closely as their formats allow, with only necessary format-native compromises.

Do not change:
- the current PDF/preview design direction
- report content or generation logic unless required for formatting parity
- section order
- export gating behavior

==================================================
1. DESIGN PARITY REQUIREMENTS
==================================================

Across PDF, DOCX, and Google export, preserve these as closely as possible:

- same section order
- same heading hierarchy
- same subheading hierarchy
- same table labels
- same spacing rhythm between sections
- same spacing inside sections
- same table structure
- same alignment rules
- same card / panel / callout feel where supported
- same visual distinction for AM Context and similar blocks
- same readable table widths and wrapping behavior
- same emphasis hierarchy for labels vs values
- same page break intent between major sections

The exports should feel like the same report in different file types.

==================================================
2. DOCX PARITY PASS
==================================================

Audit and improve the DOCX output so it resembles the PDF/preview design much more closely.

Required:
A. Section headings
- match hierarchy, spacing, and emphasis more closely
- preserve section numbering style and visual weight

B. Context blocks / panels
- where preview/PDF uses a visually distinct context block, reproduce a clean box/panel treatment in DOCX using borders, shading, spacing, or similar Word-safe styling
- AM Context should feel intentionally designed, not dumped inline

C. Tables
- preserve the same column order and hierarchy as preview/PDF
- improve column widths so they reflect the readable intent of the preview
- preserve alignment rules, especially centered columns where applicable
- avoid ugly dense table rendering
- use spacing, padding, and borders to make tables readable
- preserve header styling consistently across all sections

D. Tags / pills / labels
- where preview/PDF uses pill-like tags, reproduce the closest clean Word-safe equivalent
- if true pill styling is not feasible, use shaded rounded-feel labels or distinct bordered chips
- do not collapse them into raw comma text unless absolutely impossible

E. Spacing
- add intentional spacing before/after sections, tables, and context blocks
- avoid the “everything jammed together” Word-export look

F. Page breaks
- preserve major section breaks cleanly
- avoid splitting headings awkwardly from the content they belong to when reasonable

==================================================
3. GOOGLE EXPORT PARITY PASS
==================================================

Audit and improve the Google export/save output so it also follows the PDF/preview design closely.

Required:
A. Preserve section hierarchy
- headings/subheadings should map cleanly into Google output
- visual structure should still feel deliberate

B. Preserve block styling where possible
- AM Context and similar report blocks should not flatten into undifferentiated text
- use borders/backgrounds/spacing where supported

C. Tables
- maintain readable widths
- maintain alignment rules
- preserve header styling
- avoid raw dump formatting

D. Inline tags / example queries
- keep visually distinct formatting where possible
- do not degrade to unreadable run-on text

E. Overall visual rhythm
- spacing between sections should resemble preview/PDF as much as Google supports

==================================================
4. SHARED STYLING STRATEGY
==================================================

Create or refine a shared export styling approach so DOCX and Google export are not each reinventing the report visually from scratch.

Preferred approach:
- identify the preview/PDF design tokens / styling rules that matter most
- map them into export-safe equivalents for:
  - headings
  - section spacing
  - block styling
  - table headers
  - table cell spacing
  - alignment
  - accent usage
  - chips/tags
- keep these mappings consistent across DOCX and Google export

Important:
This is not asking for pixel-perfect parity.
This is asking for strong visual family resemblance and preserved information hierarchy.

==================================================
5. DO NOT ACCEPT THESE FAILURE MODES
==================================================

Do not leave exports in a state where:
- PDF looks polished but DOCX/Google look like raw fallback dumps
- hierarchy collapses
- context blocks flatten into plain text
- tables lose structure or readability
- spacing disappears
- tags/pills become unreadable
- exports feel like entirely different products

==================================================
6. ACCEPTANCE CRITERIA
==================================================

1. PDF/preview remains unchanged and is still the visual source of truth
2. DOCX now has clearly improved section hierarchy, spacing, tables, and context blocks
3. Google export now has clearly improved section hierarchy, spacing, tables, and context blocks
4. AM Context block looks intentionally designed in DOCX and Google export, not flattened
5. Tables in DOCX and Google export are readable and structurally aligned with preview/PDF
6. Tag/query styling remains visually distinct where supported
7. The exports feel like the same report design family, not separate unrelated outputs
8. Export flow still works
