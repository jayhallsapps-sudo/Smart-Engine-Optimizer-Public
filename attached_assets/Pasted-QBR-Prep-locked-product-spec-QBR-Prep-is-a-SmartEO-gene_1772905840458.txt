QBR Prep locked product spec

QBR Prep is a SmartEO-generated quarterly planning report for behavioral health treatment center websites.

It must:

use the same visual design language as the Monthly report

render as a continuous-page live preview

export to PDF, DOCX, and Google Drive using the same export pipeline as Monthly

require a fresh Screaming Frog crawl upload before generation

allow full inline editing after generation

autosave and allow manual save

save a durable generated report state in the database, not just print cache

QBR Prep is not:

a content calendar

a page-by-page content plan

a keyword map

a giant roadmap for the entire website

Section 6 must stay capped at 5 to 7 realistic priorities for the next quarter.

Quarter logic

SmartEO must understand standard business quarters:

Q1 = Jan 1 to Mar 31

Q2 = Apr 1 to Jun 30

Q3 = Jul 1 to Sep 30

Q4 = Oct 1 to Dec 31

Generation rule:

analyze the current quarter to date as of the report run date

label the report as planning for the next quarter

Example:

report run on March 7, 2026

analysis window = Jan 1, 2026 to Mar 7, 2026

planning quarter = Q2 2026

Comparison rule:

upcoming quarter goals must be compared against prior quarter goals

recommended goals for the next quarter should be generated from performance data, site condition, trend strength, and likely execution capacity

goals do not need to be automatically higher or lower; they need to be defensible

Left panel inputs

Use a minimal operational panel. Remove placeholder controls that do not directly improve the report.

Required:

Client

Generate as of date, default today

Required Screaming Frog upload

Generate button

Optional but useful:

How did SEO progress feel this quarter?

AM hypothesis / suspected focus next quarter

Manual audit notes

Remove:

opportunities per category

visible content capacity field

placeholder quarter controls that ask the user to do calendar math manually

Quarter selection should be inferred automatically from the generation date.

Saved report naming

Use:
QBR Prep - Client Name - Q[planning quarter] [year] - Generated YYYY-MM-DD

Example:
QBR Prep - Anchored Tides Recovery - Q2 2026 - Generated 2026-03-07

Header metadata block

At the top of QBR Prep, use a metadata block modeled after the sample QBR structure, but aligned to SmartEO’s cleaner workflow.

Fields:

Site: client display name

Domain: canonical domain

Primary Location: auto-infer from site and crawl, editable inline

Program / Positioning: auto-infer from site and crawl, editable inline

Analysis Window: current quarter to date

Planning Quarter: next quarter

Generated On: current date

Do not include content capacity.

If required data is missing:

Branded vs non-brand rules

Treat as branded:

client brand name

brand spelling variants

city-modified brand queries

founder / staff / provider names tied to the brand

unique program names tied to the brand

navigational branded searches

review-site branded searches including the brand

Treat as non-brand:

generic service queries

condition queries

treatment-modality queries

informational queries

competitor-independent “near me” queries unless the brand is explicitly present

For opportunity logic in GSC:

high-impression / low-CTR opportunities should default to non-brand only

branded queries can be reported separately, but should not dominate strategic expansion logic

Core conversion weighting

Use this priority order unless the client setup clearly says otherwise:

admits or strongest admit-proxy metric

qualified phone calls

VOB submissions

treatment-intent form submissions

GBP calls / website clicks where clearly intent-driven

assisted organic landing pages tied to conversion paths

When sources disagree:

prefer the QBR sample’s admits-first logic

use SEO and conversion principles as fallback

never let raw traffic outrank conversion relevance in recommendations

Section 5 — SEO Tier Diagnosis

Purpose:
Identify the current limiting tier using your Treatment Center SEO Priority Framework.

Output:
A short analytical block, not a table.

Required logic:
Use a rule-based model, not pure freeform AI opinion.

Tier diagnosis rules:

Diagnose Tier 1 blocked if any of these are true:

core service pages are missing, weak, ambiguous, duplicated, or cannibalized

access-to-care pages are weak, unclear, or hard to reach

conversion pathways are indirect or misleading

high-intent service traffic does not land on clear primary URLs

Diagnose Tier 2 blocked if:

Tier 1 is mostly sound

site lacks strong conditions, therapies, or primary location hubs

internal structure is disorganized

authority cannot flow cleanly between services and supporting content

Diagnose Tier 3 blocked if:

Tier 1 and Tier 2 are mostly sound

legacy duplication, thin archives, overlapping geo/service pages, or taxonomy clutter are suppressing growth

Diagnose Tier 4 blocked if:

tiers 1 to 3 are mostly healthy

comparison-stage pages like team, aftercare, alumni, about, or credibility layers are weak enough to limit choice

Diagnose Tier 5 blocked if:

tiers 1 to 4 are largely healthy

the main need is expansion through blogs, FAQs, or demand capture content

Framework guardrails:

never recommend Tier 4 or 5 before 1 and 2 are addressed

Tier 1 refreshes outrank new blog work

cleanup outranks expansion

diagnosis must cite observed evidence from crawl, conversion paths, and traffic patterns

Priority generation rules:

max 7 rows

must be realistic for one quarter

must not become a content calendar

must not list dozens of pages

must reference admits, treatment intent, site structure, or cleanup impact

Action style:
Good:

Refresh and consolidate primary detox and residential intent so Google sees one clear service path

Strengthen Verify Insurance and admissions entry points to reduce friction on high-intent traffic

Build a conditions hub to support authority flow into existing service pages

Retire overlapping near-me and legacy geo pages into the primary location architecture

Refresh highest-value assisted-conversion content tied to dual diagnosis demand

Bad:

Write 20 blogs

Build every missing page on the site

Create a page-by-page roadmap for six months

Airtable / Asana role:
Use recent work to avoid recommending things already completed or already in motion.

Screaming Frog role:
Use crawl to identify:

4xx / 5xx issues

redirects

non-indexables

missing titles

missing H1s

page-count changes

likely structural weak spots based on URL patterns

Fallback:

if audit signals are partial, still generate priorities from prior sections but flag the relevant reason or note with Manual entry needed where necessary

“Manual entry needed” behavior

Whenever data is missing or confidence is too low:

render the cell or note in lighter italic text

use the phrase Manual entry needed

do not fabricate placeholders disguised as data

Examples:

Manual entry needed: conversion source attribution unavailable for this page

Manual entry needed: location confidence low from site crawl

Manual entry needed: no recent GBP insights available
