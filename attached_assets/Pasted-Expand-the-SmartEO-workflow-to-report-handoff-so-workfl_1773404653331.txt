Expand the SmartEO workflow-to-report handoff so workflow output maps into the correct report fields by report type in a structured, configurable way.

IMPORTANT CONTEXT

The current bridge already exists and must be extended, not replaced.

What already exists:
- workflow prep data is saved at Step 6
- report pages can detect matching workflow context by report type + client
- workflow context currently appears as a WorkflowContextBanner
- the user can apply workflow prep into AM Hypothesis and Priority Checks
- current implementation uses localStorage with expiry as a temporary bridge

Do not rebuild this system from scratch.

CORE OBJECTIVE

Move the workflow handoff from a basic “carry notes forward” bridge into a more structured report-aware mapping layer, so the right workflow output lands in the right report fields depending on the report type.

PRIMARY GOALS

1. STRUCTURED FIELD MAPPING BY REPORT TYPE

Build a mapping layer that defines which workflow content can populate which report fields for each report type.

At minimum, support the currently active report pages:
- Bi-Weekly Report
- Monthly Report
- QBS

Requirements:
- map workflow content into the correct destination fields by report type
- avoid one generic “dump everything into hypothesis” model
- preserve current behavior where useful, but improve precision

Examples of workflow content that may need mapping:
- AM input by strategy area
- committed findings by strategy area
- counts / summaries
- priority themes
- technical observations
- content observations
- local observations

Important:
Do not invent a giant enterprise rules engine yet.
Do create a clear structured mapping layer that can expand later.

2. KEEP THE USER IN CONTROL

Requirements:
- users should still be able to review workflow context before applying it
- applying should feel intentional, not automatic and confusing
- if multiple destination fields are going to be populated, make that obvious
- preserve a clean UX

3. MAKE THE BANNER/IMPORT EXPERIENCE SMARTER

Refine the WorkflowContextBanner or related import UX so it can:
- show what fields will be affected
- apply content more intentionally
- optionally support partial apply if practical
- keep the UI calm and easy to understand

4. PREPARE FOR FUTURE REPORT EXPANSION

Requirements:
- structure the mapping so later report types can be added:
  - Mid-Strategy Deck
  - QBR
  - Kickoff Deck
  - Launch Deck
- do not hardcode this in a way that blocks deck-style ingestion later

5. REUSE / COMPATIBILITY RULES

- extend the current localStorage bridge for now unless a clearly better lightweight option exists
- do not break direct report-page usage
- do not break existing save/load flows
- do not replace working report pages unnecessarily
- do not overbuild final admin/template systems in this prompt

6. DEFERRED ITEMS

Do not build in this prompt:
- final database-backed workflow session persistence
- full QBS → QBR automatic derivation
- final AI-written report sections
- admin template builder
- full workflow history UI

This prompt is about smarter field mapping, not the whole future system.

DELIVERABLES

Build/refine:
- structured workflow-to-report field mapping layer
- improved report-aware apply behavior
- improved workflow context import UX
- support for current active report pages without breaking direct usage

IMPLEMENTATION REPORT REQUIRED

After building, provide a short implementation report including:
- files changed
- what was reused
- what was refactored
- what was newly added
- exact mapping model chosen
- which workflow data now maps into which report fields for each active report type
- what still remains manual
- any UX compromises
- any risks or deferred items

SUCCESS CONDITION

A SmartEO user can complete workflow prep and apply it into the correct report fields for the active report type in a structured, understandable way that reduces duplicate effort and feels like a real integrated system rather than a loose note transfer.
