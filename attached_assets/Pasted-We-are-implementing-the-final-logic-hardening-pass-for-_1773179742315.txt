PART A — SECTION 1: WHAT MATTERS MOST THIS QUARTER

Current problem:
“Goal Shift vs Last Quarter” is currently allowed to show raw “0%” without strategic interpretation. That is not acceptable. If a goal is unchanged, the system must explicitly justify why it is being held at par instead of raised or reduced.

SECTION 1 REQUIRED TABLE SHAPE

Keep these columns exactly:

Goal Type

Goal

Source

Goal Shift vs Last Quarter

Reason

Do not rename them.

A1. GOAL SHIFT DISPLAY RULES

Implement these exact display rules for “Goal Shift vs Last Quarter”:

Always calculate shift as a percentage against the prior quarter’s goal.

Formula:
goalShiftPct = ((currentQuarterGoal - priorQuarterGoal) / priorQuarterGoal) * 100

Presentation rules:

If goalShiftPct > 0, display signed percentage, example: +8%

If goalShiftPct < 0, display signed percentage, example: -12%

If goalShiftPct === 0, display: Par

Important:

“Par” is presentation only

underlying logic value remains numeric zero if needed for sorting/internal logic

exported output must also show “Par”, not “0%”

Never show raw “0%” in preview or export for this field.

Acceptance criteria:

unchanged goal => “Par”

increased goal => signed positive percent

decreased goal => signed negative percent

A2. REQUIRED REASON GENERATION LOGIC

The “Reason” column must never be generic. It must explain why the goal is:

held at par

increased

decreased

For every row in Section 1, the system must do the following:

Step 1:
Identify current planned quarter goal.

Step 2:
Identify prior quarter goal for the same metric.

Step 3:
Calculate shift classification:

PAR if equal

UP if current > prior

DOWN if current < prior

Step 4:
Pull supporting context where available from:

prior quarter actual performance

current quarter pacing to date

comparable prior-period pacing if available

tracking reliability

structural/technical constraints

conversion-path maturity

known opportunity strength

Step 5:
Generate a reason that explicitly explains why the chosen target level is justified.

A3. REASON CONTENT RULES BY CLASSIFICATION

If classification = PAR:
The reason must explain why the goal is being held rather than raised or lowered.

Acceptable content patterns:

maintaining target because performance does not yet justify expansion

maintaining target because softness appears tied to fixable tracking/structural issues rather than lack of opportunity

maintaining target because stabilization work is needed before goal expansion

maintaining target because current pacing is close enough to historical benchmark to support holding the line

If classification = UP:
The reason must explain why a higher goal is justified.

Acceptable content patterns:

prior actuals or pacing support higher target

improvement in intent, visibility, or conversion performance supports expansion

stronger funnel signals justify a more aggressive goal

If classification = DOWN:
The reason must explain why a lower goal is justified.

Acceptable content patterns:

current pacing trails relevant benchmark enough to make prior target unrealistic

unresolved structural or tracking issues reduce confidence in holding prior goal

demand softness or conversion weakness warrants a more conservative target

A4. PACING COMPARISON REQUIREMENT

If pacing data exists, Section 1 reason generation must use it.

Required comparison concept:
Compare where the account was tracking by this point in time against the comparable prior-period checkpoint.

Example:
If planning Q2 on March 10, compare current-quarter pacing through March 10 against comparable prior-quarter or prior-period pacing through the equivalent point, where data structure supports it.

Purpose:
Determine whether “Par” is actually defensible.

Decision influence:

If current pacing is materially weaker, system must consider whether flat goal is too aggressive

If current pacing is materially stronger, system must consider whether an increase is justified

If current pacing is similar, Par may be justified

Important:
If the model still chooses Par despite weaker pacing, the Reason must explicitly say why the target is still being held.

A5. MISSING OR PARTIAL DATA RULES

If data is incomplete:

Do not fabricate certainty

Do not output blank reason

Do not use “actuals pending” as the whole explanation

Do state the limitation briefly

Do still provide the most defensible rationale available

Forbidden examples:

“Actuals pending.”

“No data available.”

“Goal unchanged from last quarter.”

Acceptable pattern:
“Par. We are maintaining the prior-quarter target because available pacing does not yet justify expansion, and the main performance constraint appears to be structural/tracking-related rather than a collapse in underlying opportunity.”

A6. SECTION 1 OUTPUT REQUIREMENTS

For every row in Section 1:

Goal Shift vs Last Quarter must render correctly

Reason must be strategic, readable, and specific

Reason must reflect actual classification

Reason must reference available evidence or limitations

No generic one-liners

No repeated template phrasing across all rows if row contexts differ

PART B — SECTION 2: WHERE CONVERSIONS ACTUALLY HAPPEN

Current problem:
Top Converting Pages cannot remain blank or collapse into “No qualified data yet” just because direct GA4 conversion landing-page data is missing. We must infer what we can about engagement and likely conversion-support behavior.

SECTION 2 REQUIRED BEHAVIOR

There are two relevant subsections:

Top Converting Pages

Top Conversion Patterns

Primary fix focus:
Top Converting Pages must never be empty or dead-end when inference is possible.

B1. TOP CONVERTING PAGES FALLBACK HIERARCHY

Implement this exact fallback order for populating Top Converting Pages:

Priority 1:
Direct GA4 conversion landing-page data

Priority 2:
Call tracking landing-page or source-page data

Priority 3:
Organic landing pages with strongest commercial/admissions intent

Priority 4:
Organic/GMB/AI-LLM call source patterns tied to likely admissions-path pages

Priority 5:
Likely conversion-support pages inferred from site structure and intent, including:

homepage

contact page

verify insurance page

primary service pages

location pages

strongest high-intent organic landing pages

trust/support pages where clearly relevant

The system must stop at the first usable layer, but if higher layers are sparse and lower layers materially improve usefulness, it is acceptable to blend direct evidence plus clearly labeled inference.

B2. DO NOT DEFAULT TO DEAD-END ROWS

Do not output rows like:

“No qualified data yet”

“No qualifying conversion page identified”

unless ALL of the following are true:

no direct conversion page data exists

no call tracking page/source data exists

no organic landing page data exists

no high-intent admissions-path page inference is possible

no meaningful site-structure-based conversion-support hypothesis can be formed

That case should be rare.

B3. INFERENCE LABELING RULES

Whenever a row is not directly verified by conversion attribution, the Notes / What We’re Learning field must explicitly label it as inference.

Allowed labels:

Inference:

Directional inference:

Confidence-weighted inference:

High-confidence inference:

Moderate-confidence inference:

Low-confidence inference:

Use one of those at the start of the note when the row is inferred.

Do not add a separate confidence column unless already trivial to support. Put confidence in the note only.

B4. NOTES / WHAT WE’RE LEARNING REQUIREMENTS

Every row in Top Converting Pages must teach something useful.

Each note must do at least one of the following:

explain why the page is likely conversion-supportive

explain what kind of intent it reflects

explain what evidence supports the hypothesis

explain what tracking gap limits certainty

explain what validation step should come next

Forbidden note patterns:

generic filler

“populate this table”

“tracking needed”

“no data found” with nothing else

restating the page name with no insight

Acceptable examples:

“Directional inference: The homepage is likely supporting a meaningful share of conversion activity because it remains a primary branded entry point and routes users toward service and admissions pages.”

“Moderate-confidence inference: This detox-related page likely supports conversion activity because detox queries are near-decision and the page sits close to the admissions path, even though page-level conversion attribution is not confirmed.”

“Inference: Direct GA4 conversion landing-page data is unavailable, so this page is being treated as a likely conversion-support URL based on entry volume, treatment intent, and proximity to contact and insurance actions.”

B5. ACCOUNT-TYPE-SPECIFIC RULE

For accounts where the measurable type includes broader mixed-source outcomes such as:

organic + GMB + AI LLM calls
or similar call/source blends

the system must not stop at “no GA4 conversion data.”

Instead it must:

use available mixed-source context

look at organic/GMB/call-source patterns

infer likely page-level conversion-support URLs from that evidence stack

populate Top Converting Pages with the best defensible candidates

Anchored Tides-style behavior requirement:
If the measured business outcome stack includes organic + GMB + AI LLM calls, the system should use that context to infer likely high-intent page candidates rather than leaving the table effectively blank.

B6. PAGE CANDIDATE PRIORITIZATION RULES

When inference is needed, prioritize candidate pages in this general order:

pages directly tied to admission/contact action

contact

verify insurance

admissions-related pages

high-intent service pages

detox

residential treatment

rehab program pages

core modality/service pages

branded/high-traffic routing pages

homepage

major brand entry pages

location pages where local intent is meaningful

trust/support pages if evidence suggests they plausibly assist conversion

Do not randomly select pages. Candidate ranking must reflect:

entry importance

commercial/admissions intent

funnel proximity

likely contribution to calls or lead actions

B7. IF DIRECT DATA EXISTS

If direct conversion landing-page data or direct call tracking landing-page data exists:

use it

prioritize it over inference

still allow note commentary on intent and tracking gaps

do not label direct evidence as inference

If a row mixes direct data with interpretation, keep the evidence portion clear.
