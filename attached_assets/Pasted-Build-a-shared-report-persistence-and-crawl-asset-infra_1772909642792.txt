Build a shared report persistence and crawl asset infrastructure for SmartEO.

This is a platform-level feature. Do NOT implement it separately inside each report page. Do NOT create one-off save/load/upload logic for bi-weekly, monthly, QBR, and QBR Prep. Build one reusable system that all current and future report types can use.

==================================================
PRIMARY GOAL
==================================================

Create a shared infrastructure layer that gives all SmartEO reports the following capabilities:

1. durable autosave
2. durable manual save
3. saved report selection / reload
4. persistent Screaming Frog crawl storage per client
5. ability to upload a new crawl or select a prior crawl
6. ability to select a current crawl and an optional comparison crawl
7. shared UI controls and shared backend logic reused across:
   - bi-weekly
   - monthly
   - QBR report
   - QBR Prep
   - future report types

This must improve consistency and reduce duplication across the reporting system.

==================================================
NON-GOALS
==================================================

Do NOT:
- rebuild all report generation logic from scratch
- redesign the visual style of existing reports
- create separate save/load systems per report type
- create separate crawl pickers per report type
- remove or break existing report generation features
- overcomplicate with version graphs, diff viewers, or folder-routing logic in V1

==================================================
ARCHITECTURAL PRINCIPLE
==================================================

Use one shared reporting persistence model and one shared crawl asset library.

Every report type should plug into the same save/reload/autosave model.

Every report type that uses Screaming Frog should plug into the same crawl upload/select/compare model.

==================================================
PART 1 — SHARED REPORT SAVE SYSTEM
==================================================

Create a shared durable saved-report system for all report types.

If the current codebase already has report-specific tables, do NOT rip them out immediately if that risks breakage. Instead, create a shared abstraction that can support all reports, and migrate or bridge the current systems safely.

Target behavior:
- every report can autosave
- every report can manual save
- every report can reload a prior saved version
- every report screen has a saved-report selector
- the selector shows readable report labels, generation date, and reporting-period info

Preferred data model:
A unified saved_reports table or equivalent shared abstraction with fields like:

- id
- client_id
- report_type
- report_name
- report_period_label
- analysis_window_start (nullable)
- analysis_window_end (nullable)
- planning_quarter (nullable)
- planning_year (nullable)
- generated_on
- source_snapshot_json
- generated_report_json
- edits_json (or embedded edits if that is cleaner and consistent)
- html_snapshot (nullable)
- created_at
- updated_at
- last_saved_at
- created_by_user_id (if available)
- version_label (optional)

If a unified table is too risky right now, implement a shared service layer that normalizes existing report save structures behind one interface.

Required API/service capabilities:
- createSavedReport()
- updateSavedReport()
- getSavedReportById()
- listSavedReportsByClientAndType()
- deleteSavedReport() if already supported
- duplicateSavedReport() optional, not required for V1

Autosave behavior:
- debounce autosave after inline edits
- use the current report data and current edits, not stale closures
- stamp updated_at and last_saved_at
- do not depend on temporary print cache

Manual save behavior:
- explicit Save button on every report type
- save current report state immediately

Reload behavior:
- selecting a prior saved report should restore both:
  - generated report data
  - inline edits
- user must be able to continue editing after reload

==================================================
PART 2 — SHARED SAVED REPORT SELECTOR
==================================================

Build a reusable UI component for saved report selection.

Suggested component:
- ReportSaveSelector

It should support:
- current report type
- current client
- list prior saved reports for that client + report type
- load selected report
- display readable labels

Suggested label format:
- Bi-Weekly - Client Name - Generated 2026-03-07
- Monthly - Client Name - February 2026 - Generated 2026-03-07
- QBR Prep - Client Name - Q2 2026 - Generated 2026-03-07

Minimum UI states:
- no prior saved reports
- loading saved reports
- list of saved reports
- selected saved report loaded successfully
- error state if load fails

Use this across:
- bi-weekly
- monthly
- QBR
- QBR Prep

Do not make separate save dropdown implementations for each report page.

==================================================
PART 3 — SHARED SCREAMING FROG CRAWL LIBRARY
==================================================

Build a persistent crawl asset library for Screaming Frog uploads.

This is not one-off upload state. The uploaded crawl must persist in the system and remain selectable later.

Each crawl asset should be stored with durable metadata.

Preferred fields:
- id
- client_id
- asset_type = "screaming_frog"
- asset_name
- uploaded_at
- source_file_name
- headers_json
- rows_json
- row_count
- crawl_date if derivable, otherwise uploaded_at
- created_at
- uploaded_by_user_id (if available)
- notes (optional)
- is_active / is_deleted optional, not required for V1

Naming rule:
When a user uploads a new Screaming Frog crawl, default asset_name to:
- SF - Client Name - YYYY-MM-DD

Example:
- SF - Anchored Tides Recovery - 2026-03-07

This asset must remain in the system and be available later from a dropdown.

Do NOT overwrite previous crawls automatically.

==================================================
PART 4 — SHARED CRAWL SELECTOR / UPLOAD UI
==================================================

Build a reusable UI component for crawl management.

Suggested component:
- CrawlAssetSelector

It should support:
- show existing crawl assets for the selected client
- choose one as the current crawl
- optionally choose one as the comparison crawl
- upload a new crawl
- display upload date
- display readable asset name
- default to the latest crawl when appropriate

Required states:
- no crawls available
- list of prior crawls
- upload in progress
- upload success
- upload failure
- current crawl selected
- comparison crawl selected

For report pages:
- current crawl selector should always be present where Screaming Frog is relevant
- comparison crawl selector should be optional but supported
- upload-new should be available from the same control area

==================================================
PART 5 — CURRENT + COMPARISON CRAWL SUPPORT
==================================================

Design the system so reports can use:
- one selected current crawl
- one optional selected comparison crawl

Why:
Some reports need to compare “before vs now” so they can identify:
- new pages
- removed pages
- change in error counts
- change in redirects
- change in missing titles/H1s
- what likely changed since the prior report

You do NOT need to build a full visual crawl diff explorer right now.

You DO need to:
- persist both current_crawl_asset_id and comparison_crawl_asset_id in the report state where relevant
- expose them in generation inputs
- make them available to report generators that want comparison logic

At minimum, this must work for:
- bi-weekly
- monthly
- QBR
- QBR Prep

If a report does not use comparison, it can ignore comparison_crawl_asset_id.

==================================================
PART 8 — FRESH CRAWL WORKFLOW
==================================================

Support this real workflow:

- user opens a report page
- user sees previous saved reports
- user sees previous Screaming Frog uploads for the client
- user can either:
  - select a previous crawl
  - upload a new crawl
- new crawl is saved durably and immediately becomes selectable
- report generation can use the newest crawl by default
- optional comparison crawl can be chosen from an older upload

QBR Prep currently requires a fresh crawl before generation.
Keep that enforcement, but make it work against the shared crawl library instead of ad hoc report-page state.

If the page requires crawl freshness, the logic should read from the shared crawl assets.

==================================================
PART 9 — BACKEND / API REQUIREMENTS
==================================================

Create or extend shared backend endpoints/services for:

Saved reports:
- list saved reports by client + report type
- get saved report by id
- create saved report
- update saved report
- delete saved report if supported

Crawl assets:
- list crawl assets by client
- upload crawl asset
- get crawl asset by id
- optional delete/archive crawl asset, not required for V1

Important:
Do not duplicate the same endpoint logic 4 times.
Use shared service functions and only add thin report-specific wrappers where absolutely necessary.

==================================================
PART 13 — ACCEPTANCE CRITERIA
==================================================

This feature is correct only when all of the following are true:

1. Bi-weekly supports autosave and manual save.
2. Monthly supports autosave and manual save.
3. QBR supports autosave and manual save.
4. QBR Prep supports autosave and manual save.
5. Each report type has a saved-report selector.
6. Selecting a saved report reloads that report’s data and inline edits.
7. Screaming Frog uploads persist durably in the system.
8. Uploaded crawls are named consistently like “SF - Client Name - YYYY-MM-DD”.
9. Each relevant report page can upload a new crawl or choose an existing one.
10. Each relevant report page can choose an optional comparison crawl.
11. Selected crawl IDs persist with the saved report state.
12. Existing report previews and exports still work.
13. QBR Prep still enforces crawl freshness, but using the shared crawl asset system.
14. No report type has a custom snowflake save/load/upload system after this change.
