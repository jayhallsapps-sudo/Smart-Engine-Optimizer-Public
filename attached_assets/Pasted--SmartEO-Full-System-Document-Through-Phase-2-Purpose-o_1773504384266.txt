# SmartEO: Full System Document Through Phase 2

## Purpose of this document

This document is the working source of truth for SmartEO as it exists through the end of Phase 2, plus the planned phases that follow. It is written so that:

* a human teammate can read it and understand the product quickly
* a new developer can use it to understand architecture, feature intent, constraints, and implementation direction
* an LLM can use it as grounding context for future build prompts, audits, QA, and roadmap work
* leadership can understand what SmartEO is, what it already does, and what is still planned

This document is intentionally detailed. It is meant to capture both the product vision and the implementation reality.

---

# 1. Product identity

## 1.1 Name

SmartEO

## 1.2 What SmartEO is

SmartEO is Webserv’s internal SEO command center and guided strategy workspace.

It started as a report automation concept and evolved into a broader operating system for SEO account management, strategy preparation, workflow support, reporting, governance, and internal guidance.

SmartEO is not just a report generator.

It is designed to become a system that helps the team:

* prepare reports faster
* make better recommendations
* reduce manual dashboard hopping
* reduce rework and duplicate effort
* carry AM thinking through the reporting process
* give leadership visibility and governance control
* connect findings to execution
* eventually support deeper strategic intelligence across accounts

## 1.3 Who SmartEO is for

Primary users:

* Account Managers
* ADR
* Director of SEO
* Owner / leadership

Secondary future users:

* SEO strategists
* QA / review functions
* internal operations stakeholders

## 1.4 What SmartEO is not

SmartEO is not:

* a public-facing product
* a generic chatbot
* a freeform CMS
* a replacement for every external tool in one shot
* a final enterprise workflow engine yet

It is an internal operating platform that sits on top of data, workflows, guidance, reporting, and governance.

# 2. Core product philosophy

## 2.1 Reuse first

A core build principle throughout Phase 2 was:

* do not rebuild existing working infrastructure unless necessary
* audit existing features before replacement
* document why any replacement is necessary
* preserve prior paid-for work wherever possible

This led to a reuse-first implementation strategy rather than a greenfield rebuild.

## 2.2 Guided, not overwhelming

The product was deliberately shaped toward:

* stepper workflows
* calm desktop-first UI
* strong hierarchy
* low clutter
* clear next/back progression
* contained screens rather than giant endless forms

## 2.3 Human in control

Throughout workflow, findings, priority, execution, and reporting:

* SmartEO should inform judgment, not replace it
* AMs can revise, reject, override, and prioritize
* the product should help explain, not dictate
* automation should save time without hiding reasoning

## 2.4 Command center over generic dashboard

The SmartEO Command Center is meant to feel like:

* a strategic operating hub
* bold and obvious
* module-driven
* centered on action
* not a cramped admin dashboard

## 2.5 Governance inside the product

Admin and governance tools should live inside the product, not as a separate external admin system.

That principle carried over from the preferred pattern used in We Are WPG and shaped the in-app governance approach.

# 3. Canonical report system

SmartEO uses a canonical report lifecycle with exact names, families, audience definitions, and purposes.

## 3.1 Canonical report order

1. Kickoff Deck
2. Mid-Strategy Deck
3. Launch Deck
4. Bi-Weekly Report
5. Monthly Report
6. QBS — Quarterly Business Snapshot
7. QBR — Quarterly Business Report

## 3.2 Report families

### Slideshow-style reports

* Kickoff Deck
* Mid-Strategy Deck
* Launch Deck
* QBR

### Document-style reports

* Bi-Weekly Report
* Monthly Report
* QBS

## 3.3 Audience

### Client-facing

* Kickoff Deck
* Mid-Strategy Deck
* Launch Deck
* Bi-Weekly Report
* Monthly Report
* QBR

### Internal only

* QBS

## 3.4 Purpose of each report

### Kickoff Deck

* kickoff with a new client
* establish initial direction
* frame the start of the engagement

### Mid-Strategy Deck

* highlight work completed during discovery
* keep the client engaged
* ask questions before final strategy presentation

### Launch Deck

* present the full strategy and plan
* formalize the direction of the engagement

### Bi-Weekly Report

* high-level summary of what is happening on the account
* lightweight ongoing reporting

### Monthly Report

* higher-level monthly report with more depth than bi-weekly
* covers what happened in the prior month and what is happening next/current

### QBS — Quarterly Business Snapshot

* internal planning document
* captures what happened in the previous quarter
* captures what is planned for the next quarter
* preparation layer for QBR

### QBR — Quarterly Business Report

* client-facing quarterly review
* built downstream from QBS
* includes QBS-derived planning context plus leadership adjustments
* covers prior quarter and next quarter in detail

## 3.5 Dependency logic

The most important dependency in the report system is:

* QBS is upstream
* QBR is downstream from QBS

QBR should not be treated as an unrelated standalone deck. Structurally and strategically, it inherits from QBS.

### UX

* URL presets bypass restore intentionally

### Key file

* `client/src/lib/workflowSession.ts`

## 7.6 Finding model hardening

### Original problem

Findings were originally reconstructed from strings plus side maps, using positional IDs like `${areaId}:${index}`.
This was structurally fragile.

### Refactor

Findings became true durable objects in workflow state.

### Shape

```ts
interface Finding {
  id: string;
  areaId: string;
  areaLabel: string;
  originalBody: string;
  body: string;
  status: FindingStatus;
  selected: boolean;
  evidence?: string;
  sourceMetadata?: Record<string, unknown>;
  confidence?: "low" | "medium" | "high";
  notes?: string[];
  priority?: PriorityMeta;
  priorityOverride?: PriorityOverride;
  executionContext?: ExecutionContext;
}
```

### Identity model

* content-hash-based ID per area/body
* position-independent
* stable for current purposes

### Why this mattered

* safer revisions
* safer selection state
* safer chat binding
* future AI readiness

## 7.15 Admin auth and protection

### Goal

Replace fake UI-only admin protection with real server-enforced write authorization.

### Model implemented

* admin code verified server-side
* `POST /api/auth/admin-verify`
* write routes protected by `requireAdmin` middleware
* token passed via `X-Admin-Token`
* client stores token in sessionStorage for current session

### Protected routes

* admin guidance write routes
* admin config override write routes
* admin template/config write flows where applicable

### Read behavior

* many GET routes remain open so AMs can consume guidance/config in workflow

### Sidebar unlock UX

For admin-capable roles:

* unlock panel shown inline
* code entry + show/hide
* wrong code inline error
* green unlocked state on success
* “End admin session” clears token

### Important hardening performed

* fail-closed when `ADMIN_TOKEN` missing
* role downgrade from admin-capable → Account Manager clears token immediately

## 7.16 Priority engine

### Goal

Rank findings in a simple, explainable way.

### Initial heuristic model

Formula:

```txt
raw = (impact × 2.0) + (urgency × 1.5) − (effort × 0.8)
```

Normalized to 0–10.

### Factors

* impact
* urgency
* effort

### Buckets

* Must do now
* Should do next
* Worth doing later
* Deprioritize for now

### Inputs used

* area defaults
* regex/text signal detection

### UI

* priority badges on finding cards
* priority badges in findings review
* priority badges in finding chat
* tooltip rationale with disclaimer that this is heuristic

---

interface PriorityOverride {

### Behavior

# 14. High-level system summary for fast onboarding

If someone needs the shortest useful explanation of SmartEO at the end of Phase 2, it is this:

SmartEO is Webserv’s internal SEO operating system. It combines guided report preparation, workflow-based strategy input, finding review, AI-assisted rewriting, comments, report generation support, workflow-to-report bridges, QBS→QBR inheritance, in-app governance, admin guidance, safe config overrides, template controls, admin auth, heuristic priority ranking, manual priority overrides, execution status, Airtable/Asana reference linking, and recurring finding memory into one command center. It is not yet the final fully automated strategy engine, but it is now a real internal system for SEO account management and report preparation rather than a simple report generator.
