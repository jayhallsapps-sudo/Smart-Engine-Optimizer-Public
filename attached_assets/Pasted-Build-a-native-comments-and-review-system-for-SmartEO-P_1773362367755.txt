Build a native comments and review system for SmartEO Phase 2.

IMPORTANT CONTEXT

The following are already in place and must be extended, not replaced:
- Phase 2 foundation / reuse-first architecture
- Command Center
- canonical report registry
- report family split foundations
- repurposed left sidebar
- guided workflow shell at /workflow
- improved workflow handoff with client pre-seeding
- existing report pages and preview/edit infrastructure

Do not rebuild existing report pages or the workflow shell from scratch.

CORE OBJECTIVE

Add an internal comments and review layer so SmartEO users can collaborate on reports inside the app before reports are finalized.

The experience should take inspiration from the usefulness of Google Workspace comments:
- contextual
- lightweight
- threaded
- collaborative
- easy to resolve
- visible without clutter

REQUIREMENTS

1. COMMENT MODEL

Build a comment system that supports:
- attaching comments to a specific report section, block, text area, table, chart, or slide element where practical
- threaded replies
- author
- timestamp
- open/resolved state

For this phase, focus on a clean internal architecture and practical UI behavior.
Do not overbuild notifications, mentions, or assignments yet.

2. SCOPE OF PHASE 2 COMMENTS

Support comments in the most useful current places first.

Priority targets:
- document-style report preview/edit areas
- slideshow-style report preview/edit areas where feasible
- workflow review/assembly areas if there is a clean place to anchor comments

If full granularity is not realistic everywhere yet, use the highest-value level that fits the current architecture:
- section-level first
- then block-level where practical

Do not force fake precision if the UI cannot support it cleanly yet.

3. UI / UX REQUIREMENTS

The comment experience must:
- feel clean and integrated
- avoid cluttering the report UI
- support contextual viewing
- support resolving and reopening
- make it obvious what a comment belongs to

Preferred patterns:
- comment sidebar
- comment drawer
- inline indicator + side panel
- section/block anchor markers

Avoid:
- messy floating annotations everywhere
- giant modal-only workflow
- visual overload

4. REPORT FAMILY AWARENESS

The system must respect the two report families:

Slideshow-style:
- Kickoff Deck
- Mid-Strategy Deck
- Launch Deck
- QBR

Document-style:
- Bi-Weekly Report
- Monthly Report
- QBS

Requirements:
- comments should be structurally compatible with both families
- do not force deck and document comments into a brittle one-size-fits-all implementation
- document the current anchor level used for each family (slide-level, section-level, block-level, etc.)

5. ROLE / AUTHOR DISPLAY

Use the current in-app user context as the visible author source for now.

For this phase:
- displaying the current selected user identity/role is enough
- do not build real permission enforcement here
- do not assume localStorage role switching is secure auth
- this is an internal collaboration UI layer only

6. REUSE / COMPATIBILITY RULES

- reuse existing preview/edit/report infrastructure wherever possible
- do not replace current report pages unnecessarily
- layer comments into the existing experience
- preserve QBS design language for report-related styling
- do not break current report creation or preview behavior

7. DATA / STATE APPROACH

For this phase, choose the lightest sensible implementation that can support the current product state.

Acceptable options:
- local in-memory/stateful prototype if clearly scoped
- local persistence if appropriate
- lightweight backend persistence only if it can be done without overreaching

Important:
- do not overbuild the final enterprise-grade comment system in this prompt
- do build it in a way that can evolve later into:
  - mentions
  - assignments
  - notifications
  - approval/review workflows

8. DELIVERABLES

Build:
- comment model / structure
- comment UI in preview/edit contexts
- threaded replies
- open/resolved states
- contextual anchors
- clean report-integrated comment panel/drawer/sidebar behavior

IMPLEMENTATION REPORT REQUIRED

After building, provide a short implementation report including:
- files changed
- what was reused
- what was newly built
- what was deferred
- current anchor granularity by report family
- any UX compromises
- any architecture risks

SUCCESS CONDITION

Internal users can review and discuss specific parts of reports directly inside SmartEO in a clean, contextual, low-clutter way, without breaking the existing workflow and report infrastructure.
