MID-STRATEGY SHOULD BE A DIAGNOSTIC STRATEGY DECK

Purpose:
- analyze the client website in depth
- analyze connected integrations in depth
- identify what is structurally wrong, strategically weak, missing, broken, underperforming, or unclear
- identify what needs to be fixed
- present all of that in a clean, client-facing deck modeled closely on the provided PPTX style and the QUBS design system
- allow light manual editing after generation, not heavy manual authoring before generation

CORE PRODUCT RULES

1. The AM should only need to:
   - select the client
   - optionally attach the crawl
   - optionally toggle special sections like domain strategy if relevant
   - click generate

2. The system should already know:
   - the client domain
   - the connected integrations
   - the report date = today / generation date

3. Remove unnecessary manual-input architecture from Mid-Strategy:
   - remove Strategy Content section
   - remove IA Framework section
   - remove client sentiment
   - remove AM hypothesis
   - remove priority checks
   - remove any other boxes that make this feel like a manual report-writing form
   - keep only truly useful inputs, such as:
     - client selector
     - crawl upload/selection
     - optional client insights
     - optional domain strategy section toggle, only if needed for rare cases

4. Do not make the AM manually write slides before generation.
   The system should generate the draft slides itself.

5. If there is more than one realistic solution to a problem, the report should present multiple options.
   - maximum of 3 options
   - only present options that are realistic for the client’s brand, site, and likely comfort level
   - do not fabricate fake optionality just to sound strategic
   - when possible, identify:
     - recommended option
     - lower-lift option
     - stronger but more involved option

WHAT MID-STRATEGY SHOULD ACTUALLY ANALYZE

A. WEBSITE DEEP DIVE
The generator should crawl and analyze the website first and foremost.

It should inspect:
- homepage
- top navigation
- footer
- service pages
- program pages
- treatment pages
- what-we-treat pages
- location pages
- verify insurance / admissions / conversion pages
- about / trust / team / accreditation pages
- blog / resources / FAQ content
- internal linking structure
- crawl/indexation issues from Screaming Frog
- template consistency
- content quality and content gaps
- conversion path clarity
- menu quality and IA clarity

It should ask itself questions like:
- Is the menu too large, too small, too messy, too shallow, too deep, or too confusing?
- Are the core services clear?
- Are conversion pages easy to find?
- Is verify insurance prominent enough?
- Is the admissions path obvious?
- Is trust easy to verify?
- Are there weak pages, thin pages, duplicate pages, stale pages, or low-value blog pages?
- Is the content aligned to search intent?
- Is the site structure scalable?
- Are there gaps between what users need and what the site currently offers?
- Are there obvious crawl/indexation problems?
- Are there broken links, redirect issues, metadata issues, canonicals, noindex errors, orphan risks, or sitemap issues?
- Are there internal-linking weaknesses?
- Are local signals credible and legitimate?
- Does the site look built for users and admissions, or just for generic traffic?

B. INTEGRATION DEEP DIVE
The generator should evaluate all connected integrations and identify holes.

Check:
- GSC
- GA4
- Screaming Frog
- NSM
- GBP
- call tracking vendor if connected
- Airtable
- Asana if connected
- Ahrefs / SEMrush when helpful, not as first resort

It should identify:
- what data exists
- what is missing
- what is broken
- what is under-instrumented
- what is not mapped properly
- what tracking gaps exist
- what reporting blind spots exist
- what implementation gaps exist

It should explicitly identify:
- the hole
- why it matters
- the fix

Example:
- Missing conversion tracking on key admissions actions
- Why it matters: weak visibility into qualified lead path
- Fix: implement GA4 event mapping on verify insurance, call clicks, form submits, admissions CTAs

If there are multiple viable fixes, present up to 3 options max:
- Option 1: recommended
- Option 2: lighter/faster
- Option 3: stronger/more comprehensive
Only include multiple options when the alternatives are meaningfully distinct and brand-appropriate.

C. COMPETITIVE ANALYSIS
The system should identify relevant competitors using the client’s geography, services, and treatment focus.

This is not generic national competition.
This is local / regional, relevant addiction treatment competition.

The system should:
- infer the service area from the client website and connected data
- identify relevant competitors
- compare authority, indexed footprint, AI/snippet visibility where possible
- compare structural strengths and weaknesses
- identify where the client is behind
- identify where the client can realistically win

Do not overdo vanity metrics.
Tie competitive analysis back to:
- service coverage
- trust coverage
- conversion readiness
- content depth
- local visibility
- search structure
- admissions relevance
