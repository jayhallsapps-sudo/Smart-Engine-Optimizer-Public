Make SmartEO’s governance layer more operational by allowing selected report/mapping configuration to be edited in-app by admins instead of remaining fully code-only.

IMPORTANT CONTEXT

The governance/admin foundation already exists and must be extended, not replaced.

What already exists:
- Governance Hub
- Report Config Viewer
- Guidance Library CRUD
- workflow guidance surfacing
- workflow-to-report field mapping layer
- QBS → QBR mapping layer
- report registry
- existing report pages and workflow spine

Do not rebuild the admin system from scratch.

CORE OBJECTIVE

Move SmartEO one step further away from hardcoded behavior by making the most valuable low-risk config objects editable in-app for leadership/admin users.

PRIMARY GOALS

1. CHOOSE THE RIGHT FIRST EDITABLE CONFIG OBJECTS

Do not try to make everything editable at once.

Start with the most useful and lowest-risk editable config areas, such as:
- workflow-to-report field mapping metadata
- QBS → QBR mapping metadata
- source hints / field labels / notes / descriptions
- report config annotations
- other safe config objects you judge appropriate

Avoid high-risk edits first, such as:
- deep report routing internals
- full report registry IDs
- anything that would easily break saved report compatibility

2. PRESERVE SAFE STRUCTURE

Requirements:
- admins should be able to edit the safe parts of config
- the system should preserve the structural keys and compatibility-critical identifiers unless explicitly designed otherwise
- make it hard to accidentally break the app

3. BUILD A CALM EDITING EXPERIENCE

Requirements:
- keep the admin UI clean and desktop-first
- edit within the existing governance/config area where possible
- make changes understandable
- show what is editable versus read-only
- preserve the current config viewer value while extending it

4. PERSIST CONFIG CLEANLY

Use the lightest sensible persistence model that fits the current architecture.

Requirements:
- config edits should persist
- the app should read the persisted values where appropriate
- preserve backward compatibility with the current code-driven defaults
- if a config item has no admin-edited value yet, the current code-defined behavior should remain the fallback

5. KEEP SCOPE TIGHT

This prompt is not for:
- full WYSIWYG template building
- full report registry editing
- final rules-engine editing
- final source-routing manager
- final auth/permissions enforcement

This prompt is about making selected config editable safely.

6. REUSE / COMPATIBILITY RULES

- reuse the current governance pages where possible
- extend the current Config Viewer rather than replacing it
- do not break workflow, report pages, or saved reports
- preserve current code-based defaults as fallback behavior
- do not overbuild

DELIVERABLES

Build/refine:
- first editable config objects in admin
- persistence for those config objects
- updated config UI showing editable vs read-only areas
- runtime consumption of those edited values where appropriate

IMPLEMENTATION REPORT REQUIRED

After building, provide a short implementation report including:
- files changed
- what was reused
- what was refactored
- what was newly added
- exactly which config objects are now editable
- exactly which values remain code-only
- how fallback-to-code defaults works
- any UX compromises
- any risks or deferred items

SUCCESS CONDITION

A SmartEO admin can edit selected high-value, low-risk configuration inside the app, and SmartEO will use those persisted values while safely falling back to the existing code-defined defaults where needed.
